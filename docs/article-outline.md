## 结构

**痛点（300 字）**

- 网上流传的做法是手改 app.asar，出问题只能重装。

**功能 GIF（1 张，60s 内）**

**AI 协作过程（400 字）**
- 人定边界（不上传、不强制结束进程、不在未验证版本上写入），AI 做取证与实现。
- 先只读探测归档再动手：这一步救回了后面——见「技术难点 1」。

**技术难点（800 字，文章主体）**

1. **重打包会炸**：归档里有 47 个 unpacked 原生模块条目（node-pty、msgpackr-extract、parcel watcher），
   实体在 `app.asar.unpacked/`。用 `createPackage` 一把梭会把原生模块塞回归档，应用启动即崩。
   正确做法是从原始 header 收集 unpacked 集合，逐条目重建后复核一致。
2. **半透明面板的对比度不能拿两个色值比**：必须按「图片 → 遮罩 → 面板」三层 alpha 合成出实际底色再算。
   顺序也不能反——先出 token 再测，等于拿面板色冒充用户真正看到的底色。
3. **失败要能说清「安装有没有被改」**：错误码映射到「未修改 / 可能已修改 / 无法判定」，
   提交前失败明确安全，提交后无法自证就停在 `needs_recovery`，绝不盲目回滚。
4. **原版不可确认时禁用恢复原版**：首次接管就发现目标已被改过，就不能把这份状态冒充出厂原版。

**备份与恢复安全设计（400 字）**
- original / previous / pre-restore 三语义；备份复制后重算 SHA256，不符即删，不留假备份。
- 提交用同卷 rename，避免半截文件；提交前后各核一次 hash。
- 恢复是新前向操作，不改写历史。

**效果与限制（300 字，这部分要写得比效果重）**
- 已验证版本只有 1.18.29；其他版本只能预览。
- 真实安装验收未完成，只在合成安装上跑通闭环（如实写明）。
- 未签名；更新/修复安装后定制失效。
- 终端与语法高亮不改。
