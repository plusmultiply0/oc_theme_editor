# 基线门禁分类放行计划（2026-09-22）

> 来源：jc 真机反馈——重应用被拒「目标与首次接管快照不一致（1070 条），本次输入不可信」，
> 要求去掉快照检查。
> 结论（已对齐）：**不删检查**（它的职责是防第三方篡改归档后本工具继续写入）；
> 修的是「一刀切拒绝」——把不一致分类，官方整体更新自动重新接管，
> 第三方篡改维持拒绝。这是 `3c37369` 已登记的阻塞级缺陷的正式修复轮。

## 现状与缺口（已核实）

- F2 硬门禁第二部分：`resolveBaselineGate`（apply.ts:452-473）→ `compareWithBaseline`
  （archive-verify.ts:436-483）：当前归档非白名单条目与首次接管基线**逐条**比对，
  任何差异 → `ARCHIVE_CORRUPT` 拒绝，恢复提示只有「回到接管时状态」一条；
- 死循环成因：OpenCode 自动更新（electron-updater）整体替换 asar —— 版本号变、
  成千条目变，基线自然全不匹配；「恢复入口」只能回到旧快照，对不上新归档，
  用户无路可走（除非手动找到并删掉基线文件，无文档入口）；
- 已有可复用的判别能力：S2 落地后 apply 入口本就有 `verifyStructure`
  （锚点唯一、变更集合干净、布局一致）——「新版官方归档」恰好通过这些检查，
  判别要素齐备，缺的只是**把基线比对结果分类**而不是一票否决。

## 核心设计：差异分类，两扇门

`compareWithBaseline` 从「fail 即拒」改为返回**结构化差异**（changed / missing /
added / kindChanged 四类清单），由调用方分类裁决：

### 放行路径——「官方整体更新」自动重新接管

同时满足以下全部条件才放行（多条件缺一不可，宁拒勿纵）：

1. `out/renderer/index.html` 内的 `package.json`……（实际判据）：归档 `package.json`
   的 **version 与基线对应版本不同**（版本确实变了）；
2. **锚点仍唯一**（复用 `verifyStructure` 检查 1——新归档结构仍适用补丁）；
3. **变更集合干净**（复用检查 2——css/jpg 条目不存在，或是本工具已识别产物）；
4. **差异规模达到「整体替换」量级**（差异条目数 ≥ 基线条目的 50%，或
   `package.json` 内容变化且差异 ≥ 100 条）——排除「只改了一两个文件」的
   第三方局部篡改；量级阈值取保守值，单测固定；
5. 无「基线里有、当前归档缺失」之外的**异常信号**：unpacked 原生模块集合
   与基线记录一致（数量与路径，内容不验——官方更新必换内容但模块集合结构稳定）。

放行动作 = **重新接管（re-baseline）**：
- 以当前归档重建基线，**旧基线文件归档保留**（改名 `baseline.v1.json` 序号递增，
  不覆盖、不删除）——可追溯，符合「绝不盲目回滚/不留证据」的项目纪律；
- 首次接管快照语义不变（original 证据照旧判定），但基线从此指向新归档；
- 应用结果与操作记录里明确告知：「检测到目标已更新至 X.Y.Z，已更新基线」；
- 恢复入口语义不变（previous 主题恢复、takeover 快照恢复照常可用）。

### 拒绝路径——维持现状的行为

不满足上述全部条件（零星条目被改、条目缺失、锚点消失/变多、
变更集合被第三方占用）→ 照旧 `ARCHIVE_CORRUPT` 拒绝；
但**恢复提示改实话**：区分「看起来是官方更新但未达自动放行条件」与
「疑似第三方改动」两种文案，前者建议更新本工具/重试，后者维持走恢复入口。

## 任务分解（一项一提交）

### B1：compareWithBaseline 返回结构化差异 + 分类裁决

- `archive-verify.ts`：`compareWithBaseline` 返回
  `{ compared, drift: { changed[], missing[], added[], kindChanged[] } }`；
  新增 `classifyDrift(drift, ctx)` 纯函数实现上述五条件裁决，输出
  `'official-update' | 'suspicious'`，附判定依据明细（每条条件过/不过及数据）；
- `apply.ts`：`resolveBaselineGate` 消费分类结果——official-update → 重建基线
  （旧基线序号归档）后继续；suspicious → 照旧拒绝；
- 重新接管落证据：操作 txlog 记录 `rebaselined: true`、旧基线版本号。

**验收**：lint/typecheck 0；单测全绿。

### B2：测试——正负例各半

- 合成 asar 夹具：
  - ✅ 官方整体更新（版本变 + 全量内容变 + 锚点唯一 + 变更集合干净 +
    unpacked 集合一致）→ 放行且基线已更新、旧基线留存；
  - ✅ 差异恰好卡在阈值边界两侧（49%/51%）→ 拒绝/放行各一例；
  - ❌ 仅 1 个非白名单条目被改（局部篡改）→ 拒绝；
  - ❌ 锚点消失/双锚点 → 拒绝（哪怕版本号变了）；
  - ❌ 变更集合被第三方文件占用 → 拒绝；
  - ❌ unpacked 模块路径集合变化 → 拒绝；
  - 回归：与基线一致的正常重应用（noop/重复应用路径）行为逐字节不变。

**验收**：新增用例全过 + 全量单测无回归。

### B3：文案与文档

- 拒绝文案分两类（见设计节）；放行路径在结果/status 里可见「已检测到目标更新并更新基线」；
- README 傻瓜向说明补一句：OpenCode 自动更新后重应用，工具会自动识别并继续；
- `3c37369` 登记的缺陷在 `alpha-acceptance.md` 对应条目追加「已修（提交号）」。

**验收**：文案与代码行为一致；文档不夸口（仍如实写「局部异常改动会被拒绝」）。

## 时序与依赖

```
B1 ──→ B2 ──→ B3
```
B1 自包含；B2 依赖 B1 的分类接口；B3 收尾。全部本机可完成。

## 边界（写死）

- **不删基线比对**——防篡改职责保留，只改裁决方式；
- 自动放行**必须**五条件同时满足，任一不过即拒绝——宁可用恢复入口兜，不可纵；
- 旧基线永不覆盖删除（序号归档），重打包安全语义（提交前失败=安装原封不动）不变；
- 不动模拟预览层、不动 structural 通道的 `verifiedBy` 语义；
- 阈值（50%、100 条）写为命名常量并单测固定，不得散落在逻辑里。

## 风险与对策

| 风险 | 对策 |
|---|---|
| 官方更新被误判为篡改（用户又卡住） | 阈值取保守 + 拒绝文案给出具体不一致条目样例与前 10 条明细（现状已有），用户可拿着明细反馈 |
| 篡改伪装成整体更新（改 package.json 版本号 + 批量换文件） | 五条件含锚点/变更集合/unpacked 结构三重独立信号，伪造成本极高；剩余风险在 README 如实声明「结构级判定，非密码学校验」 |
| 重新接管后「恢复首次接管快照」语义混乱 | takeover 快照文件不动，仅基线指针迁移；UI 文案注明基线已迁移到某版本 |
