## R1 / P1：Windows ZIP 目录条目被当成多余文件，阻断发布

定位：`tools/verify-release.cjs:369–429`，`readZipCentral` 和 `checkZipMatchesDir`。

原因：先用原始名称 `endsWith('/')` 排除目录，随后才把 `\` 转成 `/`。所以 `resources\` 没被过滤，规范化后以文件身份参加比较，盘侧只枚举文件，必然报多余条目。本轮夹具得到 `zip 内多出磁盘没有的条目：resources/`；历史候选对应三个 `resources/app.asar.unpacked/.../` 目录。

修复：在所有 ZIP 检查共享的入口先规范化名称并检查安全性，再区分文件/目录。文件集合按大小和内容校验；显式目录需要验证路径合法、在盘侧确为目录。**不要简单要求“盘上全部目录都必须在 ZIP 中显式出现”**：ZIP 可以仅含文件，通过文件路径隐式表示父目录。旧方案建议盘侧目录全部一一对照，会制造新的合法 ZIP 误报。可以拒绝 ZIP 中凭空多出的目录，但不应强制每个隐式目录存在显式记录。

验收：`/` 和 `\` 结尾目录均正确识别；有/无显式父目录的合法 ZIP 都通过；额外不存在目录失败；零字节普通文件仍参与比较，不能靠 `size===0` 过滤目录。原失败候选可以只读重验来验证根因，发布仍必须使用修复后新冻结源码生成的新候选。

## R2 / P1：所谓深度校验没有验证 DEFLATE 压缩内容

定位：`tools/verify-release.cjs:455–516`，尤其 `if (method !== 0)` 分支。

原因：所有非 store 方法都仅检查数据范围后直接继续，没有解压、检查实际大小或 CRC，也没有拒绝未知压缩方法。另一个目录一致性检查只信中央目录里的 CRC/大小。因此两道检查组合也不足以验证压缩数据。

复现：中央目录声明 `file.txt` 内容为 `hello`，实际 DEFLATE 流使用非法块。`checkZipMatchesDir=[]`、`deepVerifyZip=[]`；Node 标准解压器返回 `Z_DATA_ERROR`。这是被测两个检查函数的漏检，不代表已经证明整个发布链遭到利用；额外的已登记 ZIP hash 能发现登记后的改动，但不能发现登记前就已损坏并被登记的压缩包。

修复步骤：

1. 支持 store(0) 和 DEFLATE(8)，未知方法/加密/暂不支持的 ZIP64 明确拒绝，不静默跳过。
2. 使用 Node `zlib` 验证 DEFLATE，设置输出上限及累计解压预算，避免仅信声明大小导致无限内存分配；大候选优先流式校验。
3. 检查压缩数据边界、实际输出长度、CRC；将真实解压内容与盘侧内容对应。若已有逐文件强哈希策略，复用而非只依赖 CRC。
4. 检查本地头与中央目录的名称、方法及相关 flags 一致；合法 data descriptor 的零占位字段按 ZIP 语义处理，不能盲目要求所有头字段逐字相等。

验收：有效 store/DEFLATE 通过；损坏流、解压后 CRC 不符、实际长度不符、未知方法、截断及边界异常均失败；资源上限失败可诊断。新增用例必须调用发布实际使用的校验函数，不只测夹具生成器。

## R3 / P2：路径规范化不统一，重复别名和反斜杠越界漏检

定位：同文件 `checkZipMatchesDir` 的 `new Map(...)`；`deepVerifyZip` 的原始 `seen` 和 `name.split('/')`。

复现：同包同时含 `a/b.txt` 和 `a\b.txt`，两个检查都通过。原因是比较侧 Map 静默覆盖，深度检查侧却把它们当不同名称。独立 `deepVerifyZip` 对 `..\escape.txt` 也返回空问题列表；此越界用例未证明完整门禁通过，因为目录比较通常还会拒绝它。本工具此处没有解压落盘，不能称为已复现任意文件写入漏洞。

修复：共享一个规范路径解析函数；先统一分隔符，再拒绝绝对路径、盘符、UNC、`..`、不支持的 Windows 名称；在 Map 建立前检测重复和文件/目录冲突。目录条目也必须先做安全检查，不能先跳过。目标为 Windows 时制定大小写冲突策略，避免两个条目落到同一路径。

验收：普通重复、混合分隔符别名、大小写冲突、正反斜杠越界、UNC/盘符、文件与同名目录均有明确拒绝用例。R1–R3 应合并改同一个解析模块，避免维护三套互相矛盾的规则。

## R4 / P2：worker 的失败/退出未确认仍可能被报为成功

定位：`src/core/patch/pack.ts:233–258,293–299`；`tests/unit/pack-worker-lifecycle.test.ts:189`。

复现两条：

- 收到 `{ok:true}` 后 `exit(1)`，最终 `{success:true}`；`onExit` 没检查 code。
- 收到成功后 30 秒仍不退出，`kill()` 抛错，仍 `{success:true}`；没有 exit 事件也能结算成功。

风险：下游可能开始操作仍被 worker 占用的准备区；状态机报告与注释“正常退出 + 成功回执”不符。尚不能据此认定它就是历史文件锁或启动损坏的唯一原因。上轮异步 error 监听已修好，不重新列为未修。

修复：只有成功消息和正常退出码 0 同时满足才返回普通成功。非零/null 退出返回结构化失败。宽限期届满可请求终止，但终止后仍需有界等待退出确认；kill 失败或退出未确认要返回明确失败/待恢复状态，禁止继续提交安装，并保留诊断准备区。失败结果的 recoveryHint 说明 worker 未确认退出；不要吞掉 kill 错误。同步更新那条“始终不退出仍返回成功”的测试预期。

验收矩阵：ok→exit0 成功；ok→exit1/null 失败；error、发送失败仍安全结算；ok→超时→kill 抛错/没有 exit 不得成功；重复消息/迟到事件只结算一次。超时采用假计时器；不用真实等待 30 秒。

## R5 / P1：发布冒烟无条件关闭沙箱，绿色结果不能证明默认启动

定位：`tools/smoke-packaged.cjs:134–157`；`src/main/index.ts:31` 配置 `sandbox:true`。

新冒烟参数包含 `--no-sandbox`、`--in-process-gpu` 等；文件顶部仍称与双击启动一致。命令行关闭沙箱会改变实际运行安全条件，不能把这种通过作为用户默认环境的等价验收。本次未执行此冒烟，也没有证据证明成品默认启动必然失败；问题是验证结论超出证据范围。

修复：移除正式发布冒烟中的安全降级参数，默认在保留沙箱的受支持交互会话验证候选 exe。记录实际 executable、参数、运行环境和结果；无可用会话则保留环境阻断，不产出发布资格。把历史降级运行证据注明为“非默认配置诊断”，不能追认成正常发布验收。同步清理 E2E 对同类参数的依赖，区分自动化诊断与产品验收。不建议通过关闭保护、调整安全策略来刷绿。

验收：正常配置下可见主界面、控件可用、无致命 renderer 错误、关闭干净；含安全降级参数的证据不得满足发布资格；标题或进程短时存活不能代替以上断言。

## R6 / P2：启动 E2E 对异步目标发现采用一次性快照

定位：`tests/e2e/theme-switcher.spec.ts:174–183`，`src/renderer/App.tsx:145–162`。

首个测试在标题出现后立即 `innerText()`，然后普通 `expect(string)` 检查安装路径；而发现目标需要异步 IPC 完成。标题存在不代表扫描结束，静态文本断言不会自动重试。已有一次首用例失败、后续成功的记录与此风险吻合，但本轮没重放 GUI，不能断言这是那次失败的唯一原因。

修复：先使用有界的 locator 自动重试断言等待目标路径出现，如 `await expect(page.locator('.target .muted')).toContainText(baseDir, { timeout: 30_000 })`；再检查 supported badge 与包名。若路径大小写需兼容，用 `expect.poll` 获取规范化文本。超时附扫描状态、拒绝原因、截图和 IPC 错误，禁止仅加固定 sleep 或自动重试直到绿。

验收：测试环境为 discover IPC 注入可控延迟仍通过；实际不返回目标必须失败；隔离路径限制保持原有强度。该项是测试稳定性问题，不是已证实的用户目标识别失败。
